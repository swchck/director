## [Unreleased]

### Added
- **Pre-apply validation hook.** `manager.WithCollectionValidator(func([]T) error)` and `manager.WithSingletonValidator(func(*T) error)` install a user-supplied validator that runs after fetch/deserialize and before the in-memory swap. A non-nil return rejects the version: the cluster stays on the previous known-good value (or stays empty if there is none), no snapshot is activated, and the leader retries on the next poll/WS cycle. Works in both eventually-consistent and 2PC modes; in 2PC a follower-side rejection logs `prepare_failed` and aborts the round. The same `(collection, version)` failure is logged at most once until the next successful apply, so a chronically-bad version does not flood logs across retries. Errors wrap `manager.ErrValidationFailed` for `errors.Is`. Eventually-consistent followers record apply-log status `validation_failed`. New metric: `Metrics.ValidationFailed(collection)`.
- **Strict consistency mode (opt-in two-phase commit).** Set `manager.Options.RequireUnanimousApply = true` to guarantee every alive replica runs the same config version. The leader stages each update, publishes `prepare`, waits for every alive replica to confirm, and only then publishes `commit`. A single `prepare_failed` or prepare timeout aborts the round and the leader retries on the next poll/WS cycle. See `docs/sync-protocol.md` for the full protocol and operational notes.
- `manager.Options.PrepareTTL` — bounds how long followers hold a staged snapshot before dropping it (default: `2 × WaitConfirmationsTimeout`).
- `registry.Registry.AliveInstances(ctx, service) []string` — returns instance IDs (used by 2PC target tracking so stale-heartbeat deaths drop out instead of blocking the round).
- `storage.Storage.AppliedInstances(ctx, collection, version, status) []string` — returns instance IDs with the given apply-log status.
- `storage.Storage.ResetApplyLog(ctx, collection, version)` — deletes apply-log rows for `(collection, version)`. Called at the start of each 2PC round so stale statuses from a prior aborted round of the same version don't leak into the new round's quorum check.
- `notify.Event.RoundID` (omitempty) and action constants `ActionSync`/`ActionRollback`/`ActionPrepare`/`ActionCommit`/`ActionAbort`.
- `notify.Event.InstanceID` (omitempty, JSON `instance_id`) — identifies the publisher so a replica can recognise the copy of its own event that the transport echoes back. Empty on events published by operators or external tooling, which every replica still processes.
- `notify/notifytest` — a conformance suite (`notifytest.RunContract`) that any `notify.Channel` implementation can be run against: an event reaches a peer subscriber, reaches the publisher's own subscription, survives the round trip field-for-field, and is delivered after a resubscribe. The Postgres and Redis channels run it in `e2e/`.
- `manager.LeadershipMetrics` — an optional interface (`LeaderAcquired(serviceName)`, `LeaderLost(serviceName)`) that a `Metrics` implementation may additionally satisfy to observe advisory-lock transitions, useful for tracking leadership churn and rolling-deployment handoff. Fires once per transition. The manager resolves it by type assertion when the `Manager` is constructed and skips the callbacks for an implementation that does not have them, so a `Metrics` written against any earlier version keeps working unchanged. Mirrors `storage.ActiveVersionChecker`; `NopMetrics()` satisfies it.
- `manager.SourceMetrics` — an optional interface (`SourceVersionRegressed(collection)`) that a `Metrics` implementation may additionally satisfy to observe a leader cycle declined because the source reported a version older than the one held. Fires once per declined cycle, not deduped. Resolved by type assertion when the `Manager` is constructed, exactly like `manager.LeadershipMetrics`, so a `Metrics` that does not have the method compiles and runs unchanged; `NopMetrics()` satisfies it.
- `Metrics`: `PreparePhaseStarted`/`Succeeded`/`Failed`, `FollowerPrepared`/`FollowerPrepareFailed`, `StagedDropped` for 2PC observability.
- `OnChange` on all types now returns an unsubscribe function (`func()`) to remove hooks
- `WithPersistenceTimeout` option for `View`, `SingletonView`, `IndexedView`, `IndexedViewT` (default: 10s)
- `WithSingletonViewErrorHandler` option for error callbacks on `SingletonView` persistence failures
- `WithSingletonViewPersistenceTimeout` option for `SingletonView`
- `Metrics` interface in `manager` package for observability (sync counts, latency, cache hits, follower events, WS events)
- `WithMetrics(m Metrics)` manager option; `NopMetrics()` no-op default
- Benchmark tests for `Collection`, `View`, `IndexedView` (100 to 100K items, parallel reads)
- `CONTRIBUTING.md` with development setup and PR guidelines
- `SECURITY.md` with vulnerability reporting policy
- Runtime guard: `manager.register()` panics if called after `Start()`
- **Periodic maintenance loop** for garbage-collecting old data. Configure via `manager.Options`:
  - `SnapshotRetention` (default `0` = disabled) — non-active snapshots older than this duration are removed by the leader; the current active snapshot is always preserved regardless of age. Apply-log rows for deleted snapshot versions are purged in the same transaction.
  - `InstanceRetention` (default `0` = disabled) — registry rows whose `last_heartbeat` is older than this duration are removed. Choose well above `HeartbeatInterval` (e.g. 1h+) to avoid pruning live instances during transient delays.
  - `MaintenanceInterval` (default `1h`) — how often the maintenance ticker fires. Has no effect if both retentions are zero.
- `storage.Storage.DeleteOldSnapshots(ctx, olderThan time.Time) (int, error)` — interface method; Postgres impl deletes non-active snapshots older than `olderThan` and orphaned apply-log rows in one transaction.
- `registry.Registry.DeleteStaleInstances(ctx, olderThan time.Time) (int, error)` — interface method; Postgres impl deletes instance rows whose `last_heartbeat < olderThan`.

### Fixed
- **View warm start from `ViewPersistence` never reached a reader, and destroyed the stored snapshot on its way past.** `NewView`, `NewIndexedView`, `NewIndexedViewT` and `NewTranslatedView` loaded the stored snapshot and then ran their initial compute unconditionally, so the load was overwritten before the constructor returned — the feature was write-only in four of the five view types, and only `NewSingletonView` worked, because `Singleton.Get()` reports whether the source is loaded and forced a guard there. Worse, that initial compute also *saved*: a replica whose views are built before the first sync wrote an empty result over the shared store, so every replica starting after it warm-started onto nothing and the expensive filter pipelines the store exists to skip were re-run cluster-wide. A loaded snapshot now stands, but only while the source is unloaded (zero version); as soon as the source has a version the view is computed from it and the snapshot is discarded, however stale or empty the source turns out to be — a view is a function of its source, not an independent copy. A stored `null`, an unreadable entry and a failed decode all fall through to the compute as before; a stored empty snapshot is a valid warm start. A view serving a warm start reports the zero `Version()`, and `Manager.Ready()` reads the *source* version, so warm data cannot make a replica look ready.
- **A sync request that arrived before `Start` was silently dropped.** `SyncNow` gated its send on a "running" flag set only once `Start` was entered, so a webhook delivered in the gap between the HTTP server accepting traffic and `Start` running was logged and thrown away. With `ManualSyncOnly` and polling disabled that webhook is the only trigger there is, and `Start` skips its bootstrap sync when storage already holds an active snapshot — so the config change was never picked up at all. The request channel is buffered and drained by the run loop, so a pre-`Start` request now waits there and is served when the loop comes up. Only requests made once the manager is shutting down are dropped. The two lifecycle flags (`started`, `running`) that a new call site had to choose between were collapsed into a single phase value.
- **The heartbeat did not cover the startup sequence.** It started with the run loop, i.e. after `registry.Register` and after the bootstrap sync — the longest cycle a replica ever runs, since a strict-mode bootstrap can spend `WaitConfirmationsTimeout` (30s) per collection while the Postgres registry's stale threshold is also 30s. A replica's own row could therefore go stale during its own startup, and with `InstanceRetention > 0` be deleted by maintenance GC, after which `Heartbeat` (a bare `UPDATE`) matched nothing and the instance never reappeared in `AliveInstances`: strict-mode rounds silently excluded a live replica that may have been serving stale config. The heartbeat now starts immediately after the registration and is cancelled and joined on every exit path, and a heartbeat that finds no row re-registers the instance — except on the way out, where `Stop` deregisters deliberately and a resurrected row would be a phantom instance in every peer's target set.
- **Staged 2PC values expired off the run loop.** The `PrepareTTL` timer deleted the staged entry from its own goroutine, which is exactly the mutation that made the run loop's own `commitStaged` fail with "staged entry not found": a round whose commit decision outlived the TTL lost the value it had just decided to commit, and that replica served the previous version while the rest of the cluster moved on. Expiry is now a sweep on the run loop's reconcile tick, so the invariant holds literally and the race is gone. Consequence: a staged value lives until the first reconcile tick (`HeartbeatInterval`) after its TTL, and a commit arriving before that tick applies it instead of falling back to storage. Expiry is reported as `StagedDropped(collection, "ttl")`.
- **`WithInstanceID` uniqueness was load-bearing but undocumented.** Since events are stamped with the publisher's instance ID and a replica drops its own, two replicas accidentally configured with the same ID drop *each other's* events — neither ever runs the follower path for the other and config stops propagating between them, where previously the same mistake only corrupted the apply log. The requirement is now documented on `WithInstanceID`, and `Start` warns when the registry already holds a live row for the ID (expected after a restart that reuses it, a misconfiguration otherwise).
- **Follower catch-up could move a replica backwards.** The reconcile loop compared the in-memory version against the active snapshot and applied the active one in *either* direction, guarded only by an equality check. That made a single stale `active` row a cluster-wide instruction to revert: every replica reconciles against the same row, so one leader-side ordering bug reverted every replica within one tick, and a botched manual `UPDATE` or a half-applied migration would do the same. Catch-up now rolls forward only, and so does the handling of an incoming `sync` event. A refused backward move keeps the replica on the version it holds, reports `Metrics.FollowerFailed` with the new `manager.ErrActiveSnapshotBehind` (not deduped — it is the alerting signal), and warns `refusing to move to an older active version` once per active version, naming the path that refused (`catch_up` or `sync_event`) and resetting on the next successful apply so a recurrence is reported again. The check runs both before the snapshot content is loaded and against the version actually being applied, since the version probe and the content read are separate queries. A replica whose in-memory version is zero always passes the guard, so a fresh replica still loads the active snapshot — including the `0001-01-01T00:00:00Z` version that a source without a `LastModified` signal produces, which is not "after" the zero value and would otherwise leave such a replica permanently unloaded. Moving a replica backwards is now exclusively an operator action; see the `rollback` entry below and `docs/rollback-runbook.md`.
- **Leader processed its own notify events.** `notify.Channel` implementations are broadcasts — PostgreSQL LISTEN/NOTIFY and Redis Pub/Sub deliver every event back to the publisher — but the follower handlers assumed events came from other replicas. Per 2PC round the leader re-read its own snapshot from storage, re-validated and re-staged the payload it already held in memory, wrote a duplicate `prepared` and `committed` apply-log row, and consumed its own staged entry so that the round's `commitStaged` found nothing. The manager now stamps `instance_id` on every event it publishes and drops incoming events carrying its own instance ID (logged at Debug). Events without `instance_id` are processed as before, so operator-published events and mixed-version rollouts keep working. `notify.Channel` now documents the broadcast contract explicitly, and `notify/notifytest` pins it.
- **2PC commit-phase ordering: cluster-wide rollback window.** The leader published the `commit` event before calling `ActivateSnapshot`. Notify transports (PostgreSQL LISTEN/NOTIFY, Redis Pub/Sub) broadcast back to the publisher, so the leader's own event loop consumed the staged entry first, the subsequent `commitStaged` failed with "staged entry not found", the round returned early, and the snapshot was never activated — every replica held the new version in memory while storage still pointed at the old one, and follower catch-up then reconciled the whole cluster back to the old version. `ActivateSnapshot` now runs *before* the commit is announced, making the decision durable at the moment it is made. A failed activation aborts the round exactly like a failed prepare (`StagedDropped` reason `activate_failed`, one warn per version). With the decision durable before it is announced, and with staged values expiring on the run loop, nothing can consume the staged value between the decision and the leader's own swap — so there is no half-committed leader state to report.
- **Eventually-consistent leader ordering: same rollback window, plus a permanently un-activated snapshot.** The default (non-2PC) leader swapped locally, notified every replica, waited up to `WaitConfirmationsTimeout` (30s) for confirmations and only then activated the snapshot. Followers apply the announced version within milliseconds while storage still names the old one, so every follower catch-up tick during that wait reverted them and the cluster flapped until the slowest replica confirmed. Worse, the local swap had already advanced the leader's in-memory version: if activation then failed, the next cycle's version check short-circuited and the snapshot was never activated at all — followers stayed pinned to the previous version indefinitely while the leader served the new one. The leader now fetches into a staged value, persists it, activates it, and only then applies locally and announces. The confirmation wait moved after activation, where it was already effectively advisory (a timeout used to log "activating anyway"), and a failed activation now leaves nothing advanced so the next cycle retries the same version. A consumer `OnChange` hook that panics no longer prevents the snapshot from being activated either.
- **A failed local apply was recorded as a successful 2PC commit.** After the durable commit decision, a leader whose own `commitStaged` failed logged `committed` for itself, reported `SyncCompleted`, and returned `nil` — so the apply log and `Status()` claimed a version the replica did not serve, in the one artifact used to diagnose strict-mode incidents. Unless the value actually reached memory the leader now writes no `committed` row, emits no `SyncCompleted`, and returns an error (surfaced via `SyncFailed` and `Status().LastSyncErr`). A failure caused only by a panicking consumer `OnChange` hook does count as applied — `config.Swap` publishes the value before it runs hooks, on `Collection` and `Singleton` alike — and is logged as a warning instead. That is the only way the swap can fail: with the commit decision made durable before it is announced and staged values expiring on the run loop, nothing can take the staged value out from under the round that is applying it.
- **A leader followed the source backwards and split the cluster.** `LastModified` is `max(date_updated)` (falling back to `max(date_created)`), so **deleting the most recently updated item lowers it** — ordinary content editing, no fault required. The next cycle saw a different version, fetched, activated and announced the *older* one. Replicas that received the event followed it; a replica whose 16-slot subscription buffer dropped it refused the active row on every reconcile tick from then on, alerting every 10s with no repair path for either side. A source returning `time.Time{}` reached the same state without any deletion: a forced sync stamps `time.Now()`, so the very next poll reported `0001-01-01T00:00:00Z` and re-announced the regression every cycle. Monotonicity now holds by construction rather than by refusal: a leader declines to act on a source version that is not newer than the one it holds (nothing fetched, persisted, activated or announced), reports the optional `SourceMetrics.SourceVersionRegressed(collection)` once per cycle, and warns `declining to sync a source version behind the one held` once per reported version. A declined cycle is not a failure — no `SyncFailed`, no `Status().LastSyncErr`. A forced sync (WebSocket event) mints its version from the clock whenever the source has no forward one to offer, so a deletion still propagates promptly instead of being announced backwards; polling alone now lags a deletion that lowers the maximum until the next edit. First load is unaffected, including a source that legitimately reports the zero timestamp. As defence in depth the same forward-only rule now guards incoming `sync` events, and the exclusivity claim — backward movement happens only through the operator `rollback` path — is true instead of aspirational.
- **A warm start from a stale-forward cache stranded a pod permanently.** With `ReadWriteThrough` the leader writes the cache after activating, so after a rollback the cache still named the version the operator was rolling *away* from. Nothing repaired it: the rollback handler did not touch the cache and the leader-side repair only fills a *missing* entry. Any pod starting afterwards — rolling deploy, OOM kill, eviction, scale-up — loaded that version from cache, was not corrected by storage (the active snapshot was not newer, so it was skipped), and was refused by catch-up on every tick, serving the config being rolled back for the whole freeze, with no leader able to fix it. Two changes: the active snapshot is now canonical at startup and overrides the cached value in *either* direction (skipped only when both name the same version, and left alone when storage has no active snapshot — that fallback is the point of the cache), and every replica applying a `rollback` rewrites its own cache entry from the active snapshot it just applied. All replicas write the same bytes, so the writes converge; a read-only cache strategy still writes nothing.
- **The eventually-consistent leader reported a successful sync as failed.** A failed apply-log write hard-returned after the snapshot was active, the value live in memory and the `sync` event already out: `leader sync failed`, `SyncFailed`, a non-empty `Status().LastSyncErr`, no `SyncCompleted`, and the confirmation wait skipped — for a sync every replica was already serving. The write is now logged and the cycle continues, as the 2PC path already did for the equivalent write.
- **A refused backward move erased the validator's dedup record.** Per-version failure reports shared one slot per registration, so a refusal firing on every reconcile tick evicted the record of a validator rejection: the next rejection of the same version warned again and re-fired `Metrics.ValidationFailed`, breaking its documented at-most-once-per-`(collection, version)` contract and flooding logs during exactly the incident the dedup exists for. Each report kind now keeps its own record. Kinds are a closed set of constants, so memory is bounded however often versions churn.
- **Aborting a 2PC round could leave a collection with no active snapshot.** `ActivateSnapshot` is transactional, but a transaction that commits server-side can still surface as a client error. The abort path then marked the new version `failed` while the previous active version had already been demoted to `inactive`, so a pod restarting in that window got `ErrSnapshotNotFound` and came up with no config. The snapshot is now marked `failed` only when the active version is positively known to be a different one; when it is the version being aborted, or unreadable, the snapshot is left in place and the next cycle re-activates it.
- **A fresh strict-mode `ManualSyncOnly` cluster could fail to come up at all, permanently.** A replica joins every peer's 2PC target set at `registry.Register`, the first step of `Start`, but could not receive a `prepare` until it subscribed to the notify channel several steps later — and the transports do not replay events published before a subscription existed. On a simultaneous first deploy the leader's bootstrap round therefore waited `WaitConfirmationsTimeout` on replicas that were alive, heartbeating and structurally unable to answer, and aborted. Because the manual-mode bootstrap was one-shot and the poll ticker is stopped in that mode, nothing retried: the reconcile tick ran only follower catch-up, which cannot help when no snapshot was ever activated. Collections stayed empty, `Ready()` stayed false and the cluster needed a manual `SyncNow` — long after the condition that caused the abort had passed. Two changes: the notify subscription is now established before the cache load, the storage load and the initial sync, so the window shrinks to the subscribe call itself and a replica that is still loading can answer as soon as its run loop starts (events that arrive meanwhile wait in the subscription buffer); and in manual mode the bootstrap sync is retried on the existing reconcile tick for as long as any config is unloaded, which is what `Ready()` and the startup bootstrap already mean by loaded. A source that legitimately returns no items still produces a version, so it stops the retry like any other — manual mode never turns into a scheduled poll. A subscribe failure now returns before the initial sync rather than after it.
- **A replica that had never loaded any config was silenced about it.** The 2PC abort warning is deduplicated per `(collection, version)`, which is right for "this version is bad" and wrong for "I have never come up": the one line explaining why a pod is not ready appeared once and never again, however many rounds aborted. While a collection has no version at all every abort warns; once a version is live the per-version dedup applies as before. The validator dedup and the backward-move dedup keep their own records and are unchanged.
- `safeCallHooks` now runs **all** hooks even if earlier hooks panic, collecting errors via `errors.Join`
- `View.recompute` hook panics are now recovered (previously could crash if a view hook panicked)
- `RelatedView.OnChange` is now protected by `sync.RWMutex` (was a data race if called concurrently with `Swap`)
- `CompositeView.Count()` no longer allocates merged slice when no dedup function is set
- `log.Err()` now preserves the original `error` value (supports `errors.Is`/`errors.As` in custom loggers)
- README: corrected WebSocket dependency from `nhooyr.io/websocket` to `github.com/coder/websocket`

### Changed
- **`rollback` is now the only way a replica moves to an older version, and it is documented as a procedure.** Making catch-up forward-only removed the operator lever of flipping the `active` row and waiting ~10s, so the `rollback` event — which the library consumes but never publishes — takes over that job. It already applied the active snapshot in either direction; it now also logs the apply at Warn with the from/to versions (`operator rollback applied to the active snapshot`), because overriding the monotonic guard must be visible, and records apply-log status `rolled_back` so one query confirms which replicas applied it. It also rewrites the replica's own cache entry, so the next pod to start does not warm from the version being rolled back from. Unchanged: the event must carry no `instance_id` to reach every replica including the current leader, its `version` field is ignored (the `active` row decides, so activate first), and a staged 2PC value is deliberately left alone — a replica that logged `prepared` still honours the matching `commit`. New: `docs/rollback-runbook.md` with the full procedure, replacing the raw-SQL steps operators had been using. It documents the consequence that matters most — a rollback is **not** durable on its own, because while the source still reports a newer `LastModified` the next leader cycle re-advances the collection and undoes it, so the procedure freezes leader election by holding the advisory lock until the source is fixed.
- **Leadership telemetry is no longer part of the required `Metrics` interface.** `LeaderAcquired`/`LeaderLost` were declared on `Metrics` itself, which stopped every existing implementation from compiling — `Metrics` is written by consumers, so a method added to it is a breaking change, and an implementation living inside a third-party module cannot be fixed without a coordinated release of that module. They moved to the optional `manager.LeadershipMetrics`; an implementation that has both methods behaves exactly as before, one that has neither compiles and runs as it did in v1.2.3. The methods were never part of a tagged release, so no released version is affected and there is nothing to migrate. Future telemetry is added the same way — a new optional interface, never a method on `Metrics`.
- **Single-writer invariant is now documented and enforced.** All mutations of registered config state happen on the goroutine that calls `Start` (the startup sequence, then the run loop): leader syncs, follower applies from notify events, follower catch-up, and the expiry of staged 2PC values. Consumers that assemble a cross-collection aggregate inside an `OnChange` hook depend on this — with overlapping swaps, two hook runs each observe a different mix of collection versions and the run that started first can finish last, publishing the staler assembly with no error anywhere. See `docs/sync-protocol.md`.
- **`SyncNow` no longer syncs on the caller's goroutine.** It hands a request to the run loop and returns immediately; callers that need to know when the data changed should watch `OnChange` or `Status()`. Concurrent calls coalesce into a single pending cycle, so a webhook fired once per updated collection during a bulk publish no longer queues one full cycle (a version check per registered config) per call. The `ctx` argument is now unused: the cycle runs under the context passed to `Start`, so it dies with the manager instead of with the request. A request that arrives before `Start` waits in the buffer and is served when the run loop comes up; only calls made once the manager is shutting down are dropped, with a warning.
- **Registry heartbeats moved off the run loop** onto their own goroutine and ticker, started as soon as the instance is registered so they cover the startup sequence as well. A long sync cycle — or a bootstrap that stages every collection through a full 2PC round — no longer delays them, so peers cannot declare a busy or still-starting replica dead mid-round: `WaitConfirmationsTimeout` (30s) is no smaller than the Postgres registry's stale threshold (30s). Leader election and follower catch-up stay on the run loop at the same `HeartbeatInterval` cadence. The goroutine has its own cancel and `Start` does not return until it has finished, so `Stop`'s deregister-before-shutdown ordering is unchanged.
- `registrable.fetchAndSwap` removed: both leader paths stage the value, persist it, and commit it, so nothing fetched straight into a swap any more.
- `leaderSync` and `leaderSyncForced` consolidated into single `leaderSync(ctx, reg, force)` method
- Cache write logic extracted into `cacheWrite` helper to eliminate duplication
- Persistence goroutines now use `context.WithTimeout` (default 10s) instead of `context.Background()`
- Persistence goroutines bounded by semaphore (max 2 concurrent per view); excess saves are dropped (next Swap produces a fresher save)

### Migration Notes
- `SyncNow` keeps its signature but is now asynchronous. Code that treated it as "by the time this returns, the config is swapped" — a test, an admin endpoint that reads the collection straight after — must wait for the change instead (`OnChange`, `Ready()`, or the version in `Status()`). Fire-and-forget callers (`go mgr.SyncNow(ctx)`, an HTTP handler that ignores the result) are unaffected: a call made before `Start` no longer syncs inline, but it is queued and served once the run loop comes up.
- `OnChange` now returns `func()`. Existing code that ignores the return value compiles without changes.
- `log.Err()` now stores `error` (not `string`) in `Field.Value`. Custom `Logger` implementations that type-switch on `Field.Value` and expect `string` for the "error" key should add an `error` case.
- `registry.Registry` gained `AliveInstances` and `DeleteStaleInstances`. `storage.Storage` gained `AppliedInstances`, `ResetApplyLog`, and `DeleteOldSnapshots`. Code that implements these interfaces directly must add them (the built-in `registry/postgres` and `storage/postgres` implementations do so already). The default `RequireUnanimousApply = false` preserves the eventually-consistent sync behavior; the default `SnapshotRetention = 0` and `InstanceRetention = 0` keep the maintenance loop disabled so old data is preserved as before.
- `notify.Event` gained `InstanceID`. The field is additive: custom `notify.Channel` implementations that marshal the whole struct (as `notify/postgres` and `notify/redis` do) need no change, but one that hand-rolls the payload must pass `instance_id` through or the manager will keep processing its own events.
- `Metrics` interface gained `ValidationFailed(collection string)`. Custom implementations must add it. The built-in `NopMetrics()` already does. Validators are opt-in — registrations without `WithCollectionValidator`/`WithSingletonValidator` behave identically to before.
